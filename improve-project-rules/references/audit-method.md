# Project rule audit method

## Objective and scope

Prioritize judgment, reduced overconstraint, conflict removal, and lean entry points. Preserve hard invariants, claim permission, and discoverable full methods as a safety floor. Do not use blanket percentage deletion or model brands as evidence.

Map the project's real authority chain and validation entry points. Scope may include agent/human entry points, settings/hooks, scripts/tests/CI, release/migration tools, registries/ledgers/queues, skills/prompts/adapters, and historical compatibility documents. Use risk-based sampling: exposed instructions, mandatory language, external effects, state writes, loading rules, and known drift first. Expand only when evidence warrants it.

For each significant rule family identify intent, authority, scope/mode, observable failure, actual enforcement, conflicts/drift, portability/fallback, load class, capability sensitivity, and evidence state. Many uses of “must” do not imply as many invariants; script existence does not prove its entry point, failure semantics, or coverage.

## Five layers and load classes

1. Hard invariants protect authorization, privacy, truth, integrity, correctness, and irreversible boundaries.
2. Mode contracts apply only in explicit release, migration, production, audit, checkpoint, or domain modes.
3. User value priors guide ranking without closing legitimate candidates.
4. Adaptive heuristics cover order, tools, lenses, depth, report form, and stopping.
5. Examples/resources offer templates, schemas, scripts, cases, and playbooks to load as needed.

A mixed rule may have multiple roles. Dispositions include Keep, Re-scope, Downgrade, Merge, Archive, Remove candidate, and Pending Decision. Remove candidate is not deletion authorization.

| Load class | Meaning | Typical action |
|---|---|---|
| Always | Safety or claim boundary; may be always within a mode | Keep intent, compress wording |
| Probe-gated | Needed when the self-probe or a selected mode calls for it | Move detail to discoverable resources |
| Full-only scaffold | Detailed methods for full coverage or lower-capability paths | Defer detail without destroying access |
| n/a | Background/static human material | Ordinary disposition |

Load labels can be inferred in the audit rather than required in the target project. Hard claim gates must not become removable merely because a capable model often succeeds without them.

## Hardness, capability, and independence

Hardness Test: which concrete failure is protected, in which scope, what observable counterexample follows deletion, what equivalent enforcement exists, and does repetition preserve standalone fallback?

Capability Sensitivity: could a capable path remain safe after softening, would another path miss a gate or fabricate completion, is a probe-triggered full path discoverable, and is a second weaker-model directory creating drift? Keep a short invariant plus deferred method when only the stronger path is safe. If both paths are safe and user priors do not need the rule, consider downgrade/removal. Uncertainty remains pending/debt, not a rightsizing success.

Independence Test: after copying a single project/module/skill, are safety and claim gates locally readable? Is a central contract a maintainer source or an accidental runtime dependency? Are there fallbacks without sibling skills, MCP, network, or user directories? Is repeated text an intentional Portable Core projection? Do not remove local survival in the name of deduplication.

## Result-Interference Test

For each mandatory/default-full rule, ask whether it makes a reasonable outcome unreachable:

- Does it exclude no-change, unknown, partial/mixed results, direct answers, local fixes, or novel project-specific candidates?
- Does it substitute field counts, fixed order, HTML, scores, diagrams, or tool success for actual quality?
- Does it force positive action or invented candidate competition to meet a quota?
- Does it escalate ordinary missing facts into Full, blocking, or questions without consequence analysis?
- Does it preserve a one-off preference across unrelated tasks/media?
- Does it impose rewrite-scale proof on low-risk editing or exploratory hypotheses?
- Does it transfer model work to the user via serialized questions, approvals, or needless artifact reading?
- Does it stop before the authorized goal at a plan/first patch or reask already-covered permission?

Name a concrete valid outcome damaged by the rule. Prefer triggered, proportionate language when a hard rule has no observable protected failure but does have a harmful counterexample. Examples: “do X when missing X causes Y”; “Full for consequential uncertainty, ordinary unknowns stay debt”; “enough genuine alternatives, no quota”; “smallest faithful delivery surface”; “no-change is valid with reasoning.” Preserve analysis-only and explicit stop requests while removing premature stopping.

## Safety-floor checks

Entry points containing only “use judgment” may lack gates; add a short invariant summary. Removed long methods without resource maps need restored discoverability. Missing probes may need a small probe, not default blocking of every unknown. Conflicting mandatory entries need one authority. Examples freezing exploration should become adaptable. Duplicated capability versions should return to one source plus loading/adapter layers.

For third-party skills, preserve upstream ownership/licensing and the project's authorized installation/adapter strategy. Do not relocate upstream text into project-owned skill registries or create a fork merely to change display language. Project-specific adapter policies must be verified rather than assumed. An audit is not permission to rewrite every skill.

## Consolidation and execution-space audit

Repeated incremental edits, bloated entries, or overlapping mechanisms trigger subtraction-first review. Map rule to failure, evidence, and benefit; merge equivalent protections, downgrade ordering/examples/formats, archive superseded material, or choose no-op. Add only genuinely missing boundaries. Keep full methods discoverable rather than duplicating a second body.

For high-exposure rules inspect load, decision value, conflict risk, receiver burden, enforcement source, and deferral destination. Resolve conflicts in the same file, entry point versus adapter, docs versus executable/state authority, defaults versus modes, and current task versus history. Name authoritative source, projection, and stale surface before shortening text.

## Profiles, decisions, and implementation

Default: five-layer/hardness with overconstraint as main conclusion and floor sampling. capability-focus: emphasize load/probes/interference. scaffold-heavy: explicit weaker-path or unsafe-skip evidence; defer rather than inflate entries. narrow: inspect the local wording without a repository sweep. Profiles can combine; they never create a second authority plane.

Read facts from the project rather than asking. Continue clear reversible work and ordinary unknowns. Existing authorization covering goal/action/impact remains valid. Ask only for unresolved privacy, publication, external effect, state semantics, or consequential tradeoffs. Batch minimal questions with evidence and impact; offer choices only when distinct and avoid arbitrary approval queues.

For complex approved choices record decision, affected behavior/files, authority, validation, and recovery boundary. Simple changes need only their scope. Preserve baseline work, clarify ambiguous decisions, and switch to native implementation. Compare behavior before/after, a no-extra-rule baseline, downshift scenarios, preserved gates, and discoverable loading paths. Verification scales with consequence: wording consistency, conflict examples for classifications, load discoverability for resources, and real gates/recovery for state/external effects. Repeat tests only for new changes, failures, unresolved doubt, or explicit project requirements.

## Delivery

Use chat when it faithfully carries the requested list. Durable multi-authority review or handoff uses project-local Markdown with stable anchors. Lead with conclusion, risk, evidence, and genuine pending decisions; put long inventories in appendices. HTML is optional when dependency maps/comparisons materially aid understanding; without companions, Markdown/chat remains complete. Reports and chat are independently understandable. Do not equate fewer rules, a fixture, or a script name with live assurance.
