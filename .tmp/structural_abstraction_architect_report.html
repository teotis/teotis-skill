执行摘要

总体诊断：teotis_skill 是一个精心设计的 AI 技能工作区，具有清晰的仓库模型（私有孵化 + 公开发布）和共享指导同步机制。项目在工程纪律、文档质量和架构意识上显著优于典型个人技能仓库。主要结构性压力集中在：(1) 技能间概念重叠缺少形式化边界；(2) 复杂度最高的四个技能恰好缺失评估覆盖；(3) html-response 孤立地承载了不成比例的辅助基础设施。

最重要驳回/暂缓

  • 将所有技能合并为单一框架 — 技能间领域差异显著（数学教学 vs 面试 vs 架构分析），强行统一会抹杀有意义的区别。
  • 自动同步公开仓库 — 需要人工审核的发布模型是有意设计，自动化会绕过安全审计。
  • 为 control/project.py 添加插件系统 — 当前四个子命令已覆盖全部需求，YAGNI。

已观察的结构性压力

  1. agent-handoff-planner 与 agent-orchestration-planner 概念重叠：两者都定义工作包、验收标准、验证命令、授权边界。handoff-planner 显式提到"可能升级到完整编排"。
  2. html-response 占据不成比例的基础设施：4 个脚本 + 5 个参考文件 + 1 个模板 = 约 1,060 行，超过其他任何技能的 2 倍。且无 evals。
  3. 复杂度最高的技能无评估覆盖：行数最多的四个技能（renewal-architect 888, abstraction-architect 497, orchestration-planner 359, html-response 274+辅助）全部缺失 evals。
  4. 提交信息模式退化：57 个提交中大量为 "chore: 更新 SKILL.md"，缺乏变更语义。
  5. .tmp 目录残留：包含之前的分析脚本、输出和 __pycache__，未被 .gitignore 排除。

推断与未知

  • 推断：handoff-planner 与 orchestration-planner 的边界模糊可能导致用户选择困难。
  • 推断：html-response 的高复杂度部分源于其"通用能力"定位，而非不合理的膨胀。
  • 未知：公开仓库 public/teotis-skills/ 的实际同步频率和发布流程。
  • 未知：各技能的实际使用频率和用户满意度。

结构性压力图

1. 表示重复：agent 工作包模型

agent-handoff-planner 定义了：工作包、Goal、Context、Implementation Scope、Steps、Acceptance Criteria、Verification Commands、Risks。它还有一个可选的"Orchestration-Ready Fields"部分，包含 Package ID、Allowed Paths、Dependencies、Evidence Pack。

agent-orchestration-planner 定义了：Package ID、allowed/forbidden paths、dependencies、acceptance criteria、verification commands、expected evidence、branch/worktree policy、unlock conditions。外加 INDEX.md、package-graph.tsv、state.tsv、orchestrate.sh。

压力信号：两者共享至少 6 个同名概念（工作包、验收标准、验证命令、路径授权、依赖、证据），但各自独立定义。handoff-planner 的"Orchestration-Ready Fields"本质上是 orchestration-planner 的子集。

2. 复杂度不对称：html-response 基础设施

html-response 的辅助文件（references/ + scripts/ + templates/）总计约 1,060 行，超过其 SKILL.md 本身（274 行）的 3.8 倍。其他技能均无辅助文件。这反映了 html-response 作为"通用能力"的定位——它需要处理 PDF 转换、HTML 校验、浏览器打开、模板渲染等跨领域任务。

压力信号：这些脚本（doc_to_pdf.py, pdf_to_pages.py, validate_html.py, open_browser.py）是独立的工具函数，理论上可被其他技能复用（如 abstraction-architect 生成 HTML 报告时），但当前没有共享机制。

3. 评估空白：复杂度与验证覆盖反比

最复杂的四个技能（renewal-architect, abstraction-architect, agent-orchestration-planner, html-response）全部缺失 evals。这形成了一个反直觉的模式：最需要验证正确性的技能反而最缺乏系统化测试。

4. 仓库卫生：.tmp 和提交信息

.tmp/ 包含之前的分析产物（analyze_codex_skill_opportunities.py, grothendieck_skill_analysis.html, __pycache__/），未被 .gitignore 排除。提交历史中约 70% 为 "chore: 更新 SKILL.md"，缺乏变更语义区分。

提案 1：agent-handoff-planner / agent-orchestration-planner 概念统一

结构杠杆: 高 过渡负担: 中 分类: 已验证结构机会 置信度: 高

镜头可追溯性

  • 镜头 1（补丁压力揭示缺失结构）：handoff-planner 的"Orchestration-Ready Fields"是对 orchestration-planner 概念的不完整复制。
  • 镜头 2（发现潜在领域内核）：两者的核心领域概念是"可委托的结构化工作单元"，区别仅在于调度复杂度。
  • 镜头 9（泛化必须删除异常）：统一后，6 个同名概念只需定义一次。

隐含不变量假设

两者共享的核心不变量是："一个可委托的工作单元必须声明范围、验收条件、验证手段和授权边界，无论调度方式是手动还是自动。"

保留的有意义差异

  • handoff 模式：1-3 个包，手动复制 prompt，无状态机，无 worktree 管理。
  • orchestration 模式：DAG 调度，state.tsv 状态账本，orchestrate.sh 自动推进，worktree 隔离，99-finalize 收口。

可测量复杂度删除

  • 消除 6 个同名概念的重复定义（~100 行）。
  • 用户选择简化：只需决定"手动还是自动"，而非在两个相似技能间比较。
  • 评估只需覆盖一个合同定义，而非两套。

证明义务与反驳信号

  • 反驳信号：如果 handoff-planner 的用户从不请求升级到编排，则统一的收益有限。
  • 反驳信号：如果两者的核心用户群体完全不同（如 handoff 用于外部 agent 交接，orchestration 用于内部多 agent 调度），则强行统一会增加认知负担。

过渡接缝

可以将统一的合同定义提取为共享参考文件 references/work_unit_contract.md，两个技能各自引用。这允许渐进迁移：先共享定义，再考虑技能合并。

提案 4：提交信息质量与仓库卫生

结构杠杆: 低-中 过渡负担: 低 分类: 有前景但未验证 置信度: 高

具体证据

57 个提交中，约 40 个使用 "chore: 更新 SKILL.md" 或 "chore: 更新 N 个文件" 格式。这使得 git log 无法区分：是内容修改、格式调整、bug 修复还是功能新增。

.tmp/ 目录包含：

  • analyze_codex_skill_opportunities.py（分析脚本）
  • codex_skill_opportunities/（输出目录）
  • grothendieck_skill_analysis.html（之前的报告）
  • __pycache__/（Python 缓存）

这些文件未被 .gitignore 排除（.gitignore 仅排除 ._*, public/teotis-skills/, .DS_Store）。

提议结构

  • 在 .gitignore 中添加 .tmp/。
  • commit message 改用更精确的描述，如 "docs: 更新 abstraction-architect 方法论"、"fix: 修复 orchestrate.sh AWK 边界条件"。

反驳信号

如果个人工作流中 .tmp 产物需要版本控制（如分析历史），则不排除 .tmp 更合适。但当前的 __pycache__ 残留表明这不是有意设计。



驳回或暂缓方案

R1：将所有技能合并为单一框架

驳回

8 个技能覆盖 6 个截然不同的领域（架构分析、agent 编排、HTML 交付、数学教学、模型研究、面试准备）。它们的输入类型、输出格式、用户交互模式差异显著。强行统一会创建一个"万能框架"，增加认知负担而无具体复杂度删除。

具体反例：math-tutor 需要 LaTeX 渲染和交互式推导步骤；android-career-interview-coach 需要 90 秒回答格式；abstraction-architect 需要 Mermaid 图表和交互式评审面板。这些需求无法在单一框架中优雅统一。

R2：自动同步公开仓库

驳回

AGENTS.md 明确规定"公开技能手动选择发布，行为可能与私有版不同"。公开 README 需要双语维护。自动同步会绕过这些有意设计的安全和质量关卡。

R3：为 control/project.py 添加插件系统

驳回

当前四个子命令（sync-agents, check, sync-user-skills, check-user-skills）覆盖全部需求。代码仅 237 行，结构清晰。添加插件系统是典型的过早抽象。

R4：为 html-response 创建独立的共享工具库

暂缓

html-response 的脚本（PDF 转换、HTML 校验等）理论上可被其他技能复用（如 abstraction-architect 生成 HTML 报告）。但当前没有其他技能实际需要这些功能。创建共享工具库在证据不足时是过早优化。建议在出现第二个使用者时再提取。

R5：将 SKILL.md 统一为单一语言

驳回

当前规则"skill 正文使用英语，frontmatter description 优先中文"是有意设计：英文正文保证跨平台兼容性，中文 description 便于 Claude Code 触发时识别。这不是需要修复的问题。
