# Integrate Imagegen

Use for durable project integration rather than a single generation request or visual ideation. Choose asset-only, developer-tool, or runtime-provider based on real user value. Use existing provider/configuration/CLI/asset seams instead of introducing a second generation system.

## Intelligence Adaptation Contract

- **Hard invariants**: If the user requires all final pixels to be generated, text, formulas, numbers, and visual implementation also belong to the generation model: never silently substitute local drawing or deterministic overlays. Never put credentials in tracked files, arguments, logs, manifests, or replies or copy them from other projects without authorization. Once submission returns a task ID, unknown/nonterminal tasks must be resumed rather than resubmitted. A new corrected attempt requires confirmed terminal failure with no usable asset, or a distinct authorized correction of an inspected result. Do not claim verified integration before inspecting the image, its semantics, and its real consumer path.
- **Mode contracts**: asset-only persists a session-generated asset and wires the consumer; developer-tool supplies reusable project tooling; runtime-provider joins a product/pipeline. Only external API modes introduce credential, billing, model discovery, retry, and state protocols. Paid smoke tests need authorization covering real generation and total submissions.
- **User value priors**: Let generation own composition/style/final pixels while the agent supplies verified facts and semantic boundaries. Consolidate prompts and corrections to conserve calls and user operations.
- **Adaptive heuristics**: Provider abstractions, CLIs, manifests, shared master images, model discovery, batches, and tests follow project evidence. Accuracy does not authorize a local substitute. Without an all-generated requirement, native vector/deterministic assets remain valid choices when appropriate.
- **Examples and resources**: `references/integration-playbook.md` supplies the full workflow, protocol, prompt, recovery, and evidence methods. Provider names, models, dimensions, and historical responses are examples to revalidate, never defaults to assume.

## Capability Load

Self-probe: asset or durable capability, who owns final pixels, what native seams exist, text generation or editing/reference use, can tasks resume, and what evidence proves real usability? Skip|Delta for responsibility/safety reminders; Light for asset-only; Full for tooling/runtime, paid asynchronous APIs, or uncertain protocols. Missing generation tools permit offline implementation evidence, never fake image validation.

## Integration

Read the bundled playbook for developer tools, runtime, external APIs, or live generation acceptance. Confirm native ownership, current protocol, authorized credential source, submission/poll/resume semantics, normalized results, stable asset storage, and consumer wiring. Replacing a model string alone proves none of these. Save task IDs immediately. Resume uncertain attempts. Consolidate observed corrections into bounded requests and inspect final results in the consumer.

## Composition and Output

This workflow owns engineering integration; actual generation tools supply tool semantics, and domain expertise supplies factual acceptance criteria. Existing project frameworks or ledgers remain the state authority. Missing tools/permission should be reported with completed local tests; do not pass off placeholders as generated images.

Report integration mode, entry point, default/override behavior, provider/model, real asset and consumer paths, evidence level and checks, whether paid work was submitted, resume instructions, missing evidence, checkpoint, and push status. Never output reusable credentials or full authentication headers. Default to English unless requested otherwise. Test local protocol and recovery before authorized paid smoke tests; never switch platform/model/key to blindly resubmit an uncertain task.
