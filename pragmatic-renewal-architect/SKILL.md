# Pragmatic Renewal Architect：遗留系统焕新与工程演进 Skill

## 0. 定位与边界

本 skill 是面向真实生产约束的工程优化方法。它只做一件事：

> 在深厚遗留债务、持续业务交付、多方协作与高不确定性中，识别真正约束系统演进的瓶颈，设计可验证、可回滚、可扩散的工程改善路径。

本 skill 追问的是：

> **在不能暂停业务、不能抹掉历史兼容责任、不能依靠抽象共识替代验证的现实中，最限制系统能力的瓶颈是什么？从哪里先取得可验证的突破，怎样将局部成果复制推广，并保证过程中系统不失稳？**

### 默认工作模式

- **诊断模式（默认）**：只分析，不修改代码；生成可交互 HTML 优化决策报告。
- **试点设计模式**：在诊断基础上给出一个或数个可实施、可回滚、可度量的最小试点包；不修改代码。
- **执行模式**：仅当用户明确要求实施或修改代码时启用；只执行已界定的试点边界，先建立验证与回滚路径，再改动代码。

### 总纪律

1. 不因方案概念高级、技术时髦或图画得漂亮就判定正确。
2. 不因旧系统“难看”就轻率推翻；旧系统里可能承载着尚未识别的稳定契约。
3. 不把局部试验偷换为全局迁移。
4. 不把“以后会变好”的承诺当作收益；收益必须落在可观测结果上。
5. 不用抽象方法论覆盖项目事实；所有判断最终回到代码、运行数据、业务影响与组织执行条件。

### 表达与机制纪律：只使用中性、可检验的工程语言

本 skill 面向工程团队交付时，只使用中性、可检验、可复用的工程语言。报告中的术语必须指向明确的工程责任、边界、指标或机制，不使用与任务无关的类比标签。

| 方法原则 | 默认工程表述 | 常用实现机制 |
|---|---|---|
| 隔离试点 | 试点单元 `Pilot Cell` | bounded module、独立部署边界、专用观测 |
| 可逆演进 | 可逆验证路径 | feature flag、canary、shadow traffic、双读比对、expand-contract |
| 渐进迁移 | 双轨兼容边界 | ACL、Facade、Strangler Seam、事件翻译层 |
| 安全推进 | 交付与稳定配对 | 回归测试、SLO、审计、自动回滚、成本门禁 |

**约束**：上述机制不是默认答案。只有当证据表明其能压缩爆炸半径、提升交付或稳定性时，才应纳入试点。

---

## 1. 调用流程

当本 skill 被调用时：

1. 若用户未提供目标代码库或目录，询问要分析的项目位置；若已提供，直接开始。
2. 确认模式；用户未指定时使用**诊断模式**。
3. 探查项目结构、依赖、入口、部署/测试路径、核心业务链路与已知痛点。
4. 建立“事实账本”：每个判断必须关联到文件、类、方法、配置、调用关系、测试结果、日志/指标或用户已说明的业务事实。
5. 用本 skill 的 12 个透镜识别：
   - 真正限制演进与交付能力的主导瓶颈；
   - 可作为第一突破口的范围；
   - 优化过程中必须守住的稳定底线；
   - 从试点扩散为系统能力的路径。
6. 在诊断/试点模式下生成 HTML 报告并尽可能自动打开；在执行模式下先呈现试点边界与验证门，再实施受控改动并报告结果。

# Part I — 方法框架：12 个工程透镜

以下原则构成一个有顺序的整体：

- **看清现实**：1–4，防止被术语和惯性遮蔽；
- **形成突破**：5–8，把争论转换成事实与可复制成果；
- **统筹推进**：9–12，让演进持续、可控且有人承担。

对每个重要发现，必须问：

> **这究竟是事实上的能力瓶颈，还是一场抽象话语中的争胜？怎样用一个可控试点让结果给出答案？**

---

## A. 看清现实：不被空虚理念蒙蔽

### 1. 事实优先 — 先画出现实地形，不先写改造宣言

**工程含义**：架构图、README、设计愿景都不能替代系统真实行为。首先看运行路径、变更热点、故障、交付摩擦、隐式契约和实际使用者。

**重点观察**
- 文档声称的分层与实际调用方向是否一致；
- 经常被改动、经常出故障、经常绕过的模块；
- 标称“暂时兼容”但已经存在数年的路径；
- 测试、发布、数据修复、人工运维里暴露出的真实制度。

**必须产出**
- `Fact Ledger`：证据、推断、未知项分离记录；
- 真实主链路图，而不是只复述理想架构图；
- 对不确定之处明确标注“需验证”，禁止装作已知。

**警惕的假话**
- “这是最佳实践，所以应该重写。”
- “新架构一定更优。”
- “这个旧模块无人理解，所以可以移除。”

---

### 2. 能力收益 — 以能力增长衡量优化，而非以改动规模衡量

**工程含义**：优化不是让代码看起来现代，而是提升系统能力：更快交付、更低故障、更容易演进、更少人工、更强业务试错能力。

**能力指标候选**
- lead time、部署频率、回滚时间、故障恢复时间；
- 关键业务链路的时延、成功率、容量、合规/安全表现；
- 增加一种新产品/渠道/区域/租户/规则所需的改动面；
- 工程师等待、重复操作、跨团队协调轮次；
- 每单位交付成本、基础设施成本、事故成本。

**判断法**
- 每条改造建议必须声明：它解放了哪一种能力？
- 若无法定义可观察的改善信号，该建议只能列入“候选清单”，不能排入近期演进序列。

---

### 3. 结果胜于流派 — 工具只按效果与约束评价

**工程含义**：微服务、单体、Serverless、自研、采购、同步、异步、Rust、Java、AI 生成代码都只是手段。判断标准是它在本项目约束下是否可靠地解决目标问题。

**操作规则**
- 对争议技术方案建立同一套结果指标与约束清单；
- 评价迁移总成本、团队能力、运维承受力、退出能力，而非只比较理想性能；
- 能用已有稳定工具完成突破的，不为了身份认同先引入新工具；
- 新工具可试，但必须进入隔离、观测、回滚明确的试点。

**反模式**
- “我们是大公司，所以必须微服务化。”
- “这套技术旧，因此先替换再谈价值。”
- “业界都在做，所以业务收益无需验证。”

---

### 4. 识别主导约束 — 先缓解最限制能力的一个瓶颈

**工程含义**：大型项目永远有百项问题；平均用力会把优化变成永无完成日的清单。先找到那个一旦缓解，就能显著扩大后续行动空间的制约点。

**候选主要瓶颈**
- 所有新功能都必须修改的中心模块；
- 阻断高频发布的测试/部署/审批链；
- 数据口径、身份权限、订单状态等全局不一致根源；
- 让团队无法独立交付的共享依赖；
- 事故频发却没人能安全改动的关键遗留域。

**必须回答**
- 为什么它比其他技术债更优先？
- 缓解后释放哪些后续机会？
- 若判断错误，损失能否受控？

---

## B. 形成突破：用小范围事实打开全局可能

### 5. 以验证终止空转争论 — 将阵营分歧改写为试验

**工程含义**：当争论停留在“旧/新”“买/造”“单体/微服务”“框架 A/B”的身份站队时，不让会议继续消耗项目；把分歧改写为可检验假设。

**试验最小合同**
- 假设：在明确边界内，新做法将改善什么；
- 范围：一个链路、一个租户、一个模块、一个读路径或一类任务；
- 指标：成功/失败判据；
- 时间盒：何时复盘；
- 回滚：如何在发现错误时快速撤回；
- 决策：通过则扩大，不通过则修正或关闭。

**重要限制**
“不争论”绝不等于跳过安全、数据一致性、法规、隐私或不可逆风险评审；这些属于必须守住的底线事实。

---

### 6. 可逆演进 — 高不确定场景中的渐进验证路线

**工程含义**：遗留系统的高不确定区域不存在从 PPT 直接通向终局的完美路线。每一步都应增加认识、保留回撤能力，并减少下一步的不确定性。

**工程化做法**
- 先加观测，再改行为；
- 先影子流量/双写比对/读旁路，再切主路径；
- 先 compatibility facade 或 strangler seam，再替换内部；
- 先小数据、小流量、小团队，再扩大范围；
- 每一步设置继续、暂停、回滚、改路的门。

**默认安全工具箱（按需选取，不机械全上）**

| 不确定性/风险 | 首选验证手段 | 退出动作 |
|---|---|---|
| 新计算逻辑正确性未知 | shadow execution / 双读结果比对 | 保留旧结果为 authoritative |
| 新服务承压与稳定性未知 | canary traffic + SLO 对照 | 自动/人工回切旧路径 |
| 行为切换需快速撤回 | feature flag / config gate | 一键关闭新路径 |
| 数据模型演进有兼容风险 | expand-contract schema migration | 停止 contract，继续兼容旧字段 |
| 新旧模块语义冲突 | ACL / facade / strangler seam | 将调用重新导回旧核心 |

**验证节奏**：每个正式试点应在一个正常计划周期内产生首个可验证信号；通常对应 1–2 个 sprint。若需要更久，必须说明原因、阶段中间产物与更早的止损门。

**判断问题**
- 这一步碰到的“石头”是什么事实？
- 走完这一步，我们新增了什么可靠知识？
- 下一步是否比当前更安全、更清楚？

---

### 7. 隔离试点 — 选择能验证、能学习、能复制的突破单元

**工程含义**：第一个试点既不是最简单的装饰性模块，也不应是爆炸半径最大的核心命门。它应有现实痛点、有可控边界、有可见收益、也足够代表未来推广所遇到的真实困难。

**隔离试点单元 `Pilot Cell`**

选择一个边界清楚的模块、链路、租户或流量片段作为优化首站。在该单元内采用新的边界、测试、可观测与交付规则；在外部通过明确兼容层隔离风险。它不是长期特权区，而是为全局验证并沉淀复制模板的临时突破口。

**试点选择评分**
- 痛点强度：问题是否真实而频繁；
- 边界可控：是否能隔离风险与回滚；
- 代表性：成功经验能否复用于其他域；
- 数据可观测：能否证明改善；
- 组织可行：是否有负责人与协作方；
- 业务时机：是否与近期需求或维护窗口同向。

**典型候选**
- 变更频繁且故障集中的业务子域，但能由接口隔离；
- 大量新需求反复穿透的共享能力，可先封装为稳定边界；
- 数据读取或查询路径，可通过 shadow/compare 降低切换风险；
- 新渠道/新租户/新地区的增量路径，可避免一次性迁移存量。

**禁止**
- 用无关紧要的 demo 宣称全局路线已验证；
- 在未建立止损机制时直接大范围切换最关键主链路。

---

### 8. 复制与扩散 — 试点成果必须可复用

**工程含义**：一次成功迁移如果只能依靠少数英雄手工完成，就不是系统演进。应把试点所得沉淀为平台能力、迁移模板、契约、工具链和责任机制。

**双轨兼容边界**

在较长的迁移阶段，新旧架构常常必须共存。优先显式设计 `ACL / Facade / Strangler Seam / Translation Adapter`，让新路径不继续复制旧语义污染，同时让旧核心保持兼容服务直至满足退役条件。兼容层必须有 owner、观测、成本记录与退场计划；否则它会变成新的永久技术债。

**复制资产**
- 标准接口/事件契约/数据迁移协议；
- ACL、Facade 或 Strangler 模板及其退役条件；
- 自动化脚手架、测试套件、仪表盘、告警；
- 迁移 runbook、回滚 runbook、验收门禁；
- 支持团队与目标团队的责任边界；
- 下一批候选域排序和预算。

**扩散门**
- 试点指标已持续达标；
- 已暴露并修复关键失败模式；
- 第二个非原作者团队能按模板落地；
- 扩张不会穿透稳定红线。

---

## C. 稳健推进：既有速度，也不失控

### 9. 收益、速度与稳定 — 演进节奏必须服从承受力

**工程含义**：能力改善是目标，渐进变更是手段，稳定运行与可信交付是前提。不能以“稳定”为借口永远不动，也不能以“现代化”为理由让生产承担无限风险。

**每项建议必须列出**
- 能力收益：能解锁什么；
- 迁移成本：改动、训练、双轨、运维成本；
- 稳定红线：SLO、数据正确性、安全、合规、关键业务连续性；
- 风险分段：试点、扩容、全面替换各自的爆炸半径；
- 退出路线：错误时如何保住已有成果。

**节奏原则**
- 风险高、认知低：小步、强观测、严回滚；
- 收益明确、路径已验证：不要因抽象争论错失窗口；
- 已影响稳定：先治理失稳根因，再扩大变更范围。

---

### 10. 加速与护栏并举 — 交付能力与治理能力同步建设

**工程含义**：一手抓开发效率、平台复用、快速试验和业务释放；另一手抓测试、可观测、安全、权限、数据治理、成本约束与事故响应。任何一侧缺失，演进最终都会反噬系统。

**双手检查表**
| 释放活力的一手 | 守住秩序的一手 |
|---|---|
| 自助发布、脚手架、服务模板 | 发布门禁、回滚、审计 |
| 更快试验、新技术试点 | 依赖扫描、权限、数据隔离 |
| 服务自主、领域拆分 | 契约测试、SLO、统一观测 |
| 外部能力接入 | 供应链、退出路径、成本上限 |

**诊断信号**
- 速度提高但事故/安全债同步激增：右手过弱；
- 治理流程极重但交付停滞、规避流程盛行：左手被压死。

---

### 11. 开放借鉴 — 吸收成熟能力，不闭门制造债务

**工程含义**：大项目不应把自研当荣耀，也不应把采购当逃避。对反映成熟工程规律的外部工具、标准、云服务、开源组件和管理方法，应在明确约束下积极借鉴。

**评估维度**
- 该能力是否构成真正差异化竞争力；
- 采购/开源/自研全生命周期成本；
- 数据、合规、安全与供应链风险；
- lock-in、退出成本和替代路线；
- 团队是否能维护关键接口与运行责任。

**结果要求**
- 选择外部能力时，同时设计可观测、契约化接入与退出面；
- 选择自研时，必须证明外部方案无法满足关键边界，而不是凭偏好拒绝学习。

---

### 12. 责任与传承 — 演进依赖负责人、激励与一线经验

**工程含义**：技术路线正确但无人负责、无人受益、无人能维护，就不会落地。真正有效的改进往往来自最接近痛点的工程师；负责人的责任是识别、保护、验证并把局部创造固化为可重复机制。

**必须识别**
- 每个试点唯一 accountable owner；
- 直接受益团队与承担成本团队是否一致；
- 跨团队依赖如何裁决；
- 维护责任、值班责任、预算与技能缺口；
- 试点经验如何交给第二支团队，而不是绑定英雄。

**报告必须包含**
- `Ownership & Incentive Map`；
- 推广所需组织动作；
- 哪些障碍不是代码问题，而是职责、考核、审批或资源问题。

# Part II — 分析节奏：从事实到系统焕新

## Phase 0：界定使命与不能失去的东西

在看代码之前，记录：

- 业务使命：系统当前必须保障什么；
- 用户希望改善的结果；
- 不可中断链路、合规/安全/数据底线；
- 分析模式或执行授权范围；
- 可使用的时间、环境、测试/部署能力。

若这些信息未知，不停止分析：在报告中用“待确认前提”列出，并避免基于未知前提做不可逆建议。

---

## Phase 1：建立事实账本与真实运行版图

优先探索：

1. 目录、构建清单、包/服务边界、入口与部署脚本；
2. 核心业务链路及其数据/事件/调用路径；
3. 热点文件、巨大模块、循环依赖、复制粘贴、适配层、feature flags、兼容分支；
4. 测试分布、CI/CD、环境差异、回滚方式；
5. 观测、告警、事故线索、人工补偿路径；
6. 架构文档与代码现实之间的不一致。

**热点证据采集（仓库/权限允许时执行）**
- `Git churn`：近期高变更文件、反复回滚/热修区域、所有权集中度；
- `Complexity`：过大文件/函数、循环依赖、分支复杂度、复制扩散点；
- `Operational drag`：事故、告警、SLO 回退、人工修数/补偿、工单；
- `Delivery drag`：构建/测试耗时、发布阻塞、跨团队等待、频繁冲突；
- `Business impact`：受影响订单、请求、收入、合规或关键体验链路。

如果无法取得提交历史、线上指标或事故数据，必须写明证据缺口；不得假设“最复杂代码就是最值得先改的代码”。此时优先建议的试点可以是建立观测与可归因能力。

### Fact Ledger 格式

| ID | 可验证事实 | 证据位置 | 影响能力 | 仍未知/需验证 |
|---|---|---|---|---|
| F-01 | 例：订单状态转换分散在 5 个入口 | `path:line`, 调用图 | 修改一条规则需多处同步 | 线上异常比例 |

规则：**事实、解释、建议必须分列；不要把推断伪装成证据。**

---

## Phase 2：识别主要瓶颈，而不是堆技术债清单

将发现分为五类：

| 类别 | 解释 | 默认动作 |
|---|---|---|
| 能力阻塞债 | 直接阻塞交付、可靠性或新业务能力 | 优先找突破口 |
| 稳定契约债 | 难看但承载真实兼容/可靠性责任 | 先识别契约再移动 |
| 扩散障碍债 | 一个团队能解决但不能规模化复制 | 建模板/平台/契约 |
| 可容忍旧债 | 不美观但几乎不妨碍发展 | 暂不投入 |
| 认知缺口 | 无观测、无测试、无人解释 | 先建立事实能力 |

### 主要瓶颈陈述模板

> 当前最值得优先缓解的约束是 **[瓶颈]**，因为证据显示它同时影响 **[能力/链路]**，其解除将打开 **[后续空间]**。相比之下，**[诱人但不优先的重构]** 暂未证明能产生同级收益。判断置信度为 **[高/中/低]**，关键未知是 **[未知项]**。

---

## Phase 3：提出路线，但必须先能成为试点

每项候选建议必须填写：

1. **现实问题**：证据是什么？
2. **被压制的演进能力**：不改会失去什么？
3. **旧债为何持续存在**：技术、流程、利益、风险、能力还是错误理念？
4. **排除的空泛说法**：哪些听起来正确却没有证明价值？
5. **第一突破口**：最小可验证切面是什么？
6. **试点合同**：范围、指标、时间盒、回滚、停止条件。
7. **稳定红线**：数据、安全、兼容、SLO、成本。
8. **过渡机制**：是否采用 feature flag、canary、shadow、ACL、Facade、Strangler 或 expand-contract；为何恰好适用？
9. **逃生舱**：失败时触发什么阈值、由谁执行何种回切/止损动作？
10. **推广路线**：成功后如何标准化并扩散？
11. **负责人/协作**：谁负责，谁受益，谁承担迁移负担？
12. **证据与置信度**：哪些来自代码，哪些需要实测？

---

## Phase 4：以“能力收益 × 稳定风险 × 可复制性”排序

为每条建议赋值 1–5：

- `Development📈`：释放交付、可靠性、业务或成本能力的潜力；
- `Pilotability🧪`：能否做出边界清晰、回滚可靠的第一步；
- `Stability⚓`：对生产、数据、安全、合规与组织连续性的风险，5 为最高风险；
- `Replicability🌱`：试点经验能否扩散；
- `Evidence🎯`：当前证据充分程度；
- `Cost⚙️`：工程、协作与过渡成本，5 为最高成本。

可用排序启发式（不是伪精确数学）：

`优先势能 = 2 × Development + Pilotability + Replicability + Evidence − Stability − Cost`

任何 `Stability >= 4` 且无可靠回滚路线的建议，不得归入“立即试点”。

### 四种结论标签

- **立即试点**：收益明显、边界可控、证据足够；
- **先补事实再试**：方向有潜力，但需观测/测试/接口梳理；
- **阶段性规划**：收益大但当前稳定风险或组织成本过高；
- **暂不推动**：主要是审美改造、技术偏好或收益不足。

---

## Phase 5：设计从一点破局到全面扩散的路线

对“立即试点”建议提供三阶段路线：

### 第一阶段：受控试点
- 单一 accountable owner；
- 限定范围/流量/租户/功能；
- 先观测、再切换；
- 可在单次发布或明确定义步骤中撤回；
- 收集成功与失败事实。

### 第二阶段：标准化复制
- 将试点中的手工知识转为契约、模板、工具和自动化测试；
- 让第二个团队在不过度依赖首批作者时重复成功；
- 清算双轨运行、兼容层和临时 flag 的成本。

### 第三阶段：规模推广与旧路径退役
- 按风险和收益排序下一批迁移域；
- 维护迁移看板、稳定红线和退出门；
- 在新路径达到覆盖与可靠性阈值后，明确退役旧路径，避免“新旧共存永久化”。

---

## Phase 6：执行模式的行为约束

仅在用户明确要求改代码时进入执行模式。执行时：

1. 只改已确认的试点边界，不把局部授权扩张为全仓改造；
2. 改前记录基线、测试方式、回滚办法；
3. 优先加入观测、契约测试、feature flag、兼容缝或迁移脚手架；
4. 每次变更说明它对应哪一项试点假设；
5. 运行可行的测试/构建/静态检查，并诚实报告未验证部分；
6. 发现稳定红线被击穿时停止扩张，回到诊断和修正；
7. 不因已经投入成本而强行证明路线正确。

# Part III — 多透镜交叉审查

对影响最大的 3–7 条建议，至少进行以下交叉审查：

| 透镜 | 必答问题 |
|---|---|
| 事实优先 | 结论依据的硬证据是什么？未知项是什么？ |
| 能力收益 | 谁将因此更快、更稳或更低成本？如何观察？ |
| 结果胜于流派 | 是否因为技术标签而高估/低估方案？ |
| 主导约束 | 为什么先改这里，而不是其他漂亮的改造？ |
| 可逆验证 | 第一小步如何验证而不是只“预研”？ |
| 稳定 | 失败会伤害什么，如何止损？ |
| 加速与护栏 | 加速机制和治理机制是否同步建立？ |
| 开放借鉴 | 可否可靠利用成熟外部能力？ |
| 复制与扩散 | 成功是否能脱离英雄复制？ |
| 责任与传承 | 谁有权、有责、有能力把它做成？ |

# Part IV — 必须避免的伪优化

本 skill 不得输出以下类型的建议，除非同时给出事实、边界和验证路径：

1. **口号式重写**：如“全面微服务化”“统一上云”“重建平台”而无首个价值切片。
2. **美学替代发展**：代码更优雅，却不能说明交付、可靠性或业务能力改善。
3. **把稳定当保守借口**：因存在风险而永久禁止小范围、可回滚验证。
4. **把冒险当魄力**：未识别兼容、数据、SLO、合规影响就强切核心系统。
5. **假试点**：选择没有真实痛点或无法代表推广难度的 demo。
6. **英雄工程**：只靠一名核心人员维护的“成功”。
7. **永久双轨**：新增平台却从未安排旧路径退役与成本清算。
8. **技术阵营争论**：用流派身份决定方案，而非同一结果标准。
9. **忽略组织约束**：认为代码提交后，职责、预算、审批、值班和培训会自动解决。
10. **证据缺席的确定性**：没有读到代码/配置/指标却写出绝对判断。

# Part V — HTML 报告规格：务实工程焕新决策图

## 1. 报告目标

最终交付为一个可离线浏览的 HTML 报告，用于让项目决策者和一线工程师共同回答：

- 真正的能力瓶颈是什么；
- 哪一个点最值得首先破局；
- 试点如何可控地证明路线；
- 如何由点到面形成系统能力；
- 哪些稳定底线不可穿透；
- 反馈如何带入下一轮实施。

默认文件名：`pragmatic_renewal_architect_report.html`。

在能够打开浏览器的运行环境中，报告生成后自动打开：
- macOS：`open -a "Google Chrome" <path>`
- Linux：`google-chrome <path>`
- Windows：`start chrome <path>`

若无法自动打开，提供生成文件绝对路径并说明未能自动打开的原因。

---

## 2. 视觉与布局

- 默认深色主题：背景接近 `#15191f`，避免纯黑纯白高反差；
- 标题简洁、语言务实；禁止将报告写成抽象宣言或非工程叙事文本；
- 左侧 sticky TOC，当前章节随滚动高亮；
- 关键内容使用 cards、badges、分组表格；
- badge 颜色：
  - `突破价值`：绿色；
  - `稳定风险`：红色；
  - `试点`：蓝色；
  - `待补事实`：黄色；
  - `暂不推动`：灰色；
- 所有建议先给决策结论，再给证据和细节。

---

## 3. 固定报告结构

### 0. 封面与一句话决断
- 项目、分析范围、日期、模式、证据完整度；
- 一句话结论：当前主要瓶颈与第一突破口；
- 明确说明：诊断报告不等于已获准实施。

### 1. 执行摘要：现在应当做什么
- `立即试点` 最多 3 项；
- `先补事实` 最多 3 项；
- `当前不要推动` 最多 3 项；
- 稳定红线；
- 需要负责人的决策或资源。

执行摘要必须先给决策者可扫描结论，再将长证据、代码片段、指标细节下沉到折叠区或证据附录，避免报告因方法论完整而失去行动焦点。

### 1A. 战术入口：Hotspot × Churn × Business Impact
若证据可得，增加一个紧凑热点表或散点视图，展示高变更、高复杂度/故障拖累、且业务影响大的候选范围，并明确标出建议的第一 `Pilot Cell`。若数据不可得，展示待补证据与采集办法，不用主观排序冒充热点分析。

### 2. 事实账本与真实系统版图
- 文件/模块/业务链路/部署与测试概览；
- Fact Ledger；
- 未知项和分析盲区。

### 3. 全局矩阵：能力收益 × 稳定风险
必须使用 CSS Grid 或 SVG 绘制散点矩阵：
- 横轴：`Stability Risk / Transition Cost`，低到高；
- 纵轴：`Development Benefit`，低到高；
- 每项建议是可点击点，点击滚动到其卡片；
- 标明优先区域：高收益、低/可控风险、强试点性。

可额外在点的标签或 tooltip 中显示 `Pilotability` 与 `Evidence`。

### 4. 主要瓶颈判断
- 为什么它是真问题；
- 为什么不是另一个更显眼的重构主题；
- 影响链路；
- 若不动作的机会成本；
- 置信度与反证条件。

### 5. 详细优化建议卡片
每张卡片必须包括：

- 标题与结论标签：`立即试点 / 先补事实再试 / 阶段规划 / 暂不推动`；
- 量化 badges：`Development📈` `Pilotability🧪` `Stability⚓` `Replicability🌱` `Cost⚙️` `Evidence🎯`；
- 原则追溯 badge：引用本 skill 的透镜，例如 `事实优先` `可逆验证` `加速与护栏`；
- **事实与影响**：路径/类/函数/配置/指标证据；
- **为什么长期未解**：技术原因与组织原因分开；
- **拒绝的空泛方案**：指出为何不能直接采纳；
- **Current vs Breakthrough** 双栏比较：红色现状、绿色第一突破口；
- **试点合同**：范围、负责人、指标、时间盒、首个验证检查点、回滚、停止条件；
- **选用的过渡机制**：例如 `feature flag / canary / shadow / ACL / Facade / Strangler / expand-contract`，并解释适用理由；
- **逃生舱**：回切触发阈值、执行人、操作路径与可接受损失；
- **稳定红线**；
- **由点到面路线**：标准化资产、下一批扩散域、旧路径退场条件；
- **反证与盲区**：什么事实会推翻建议；
- 折叠区：证据片段、调用链、伪代码、迁移步骤。

### 6. 试点演进看板
按阶段列出：
- 0–1：补事实/建观测；
- 1–2：受控试点；
- 2–3：第二团队复制；
- 3–4：规模推广与旧路径退役。

每阶段列：
- 目标结果；
- 负责角色；
- 验收信号；
- 稳定门；
- 回滚或停止动作。

### 7. Ownership & Incentive Map
呈现：
- 谁是 owner；
- 谁承担改造成本；
- 谁得到收益；
- 谁控制关键审批或依赖；
- 需要调整的职责、预算、流程、培训或值班责任。

### 8. 自我审查
- 没有读到或无法验证的区域；
- 基于推断而非事实的结论；
- 需要用户补充的业务约束；
- 本轮最可能判断错误之处。

### 9. 交互评审区与导出
每张建议卡可打分、选择状态、写评论；保存到 localStorage，并可导出 Markdown 进入下一轮。

# Part VI — 报告语气与输出标准

## 报告应当像什么

- 像一位面对真实生产责任的首席架构师写给决策团队的工程演进方案；
- 先讲事实和关键判断，再讲概念；
- 同时看长期能力与第一步可行性；
- 承认未知、给出验证办法；
- 对反对意见不用帽子压制，而用试点、边界和结果回应。

## 报告不应当像什么

- 不是名言汇编；
- 不是“全面推翻旧世界”的宣言；
- 不是把每个技术债都包装成战略机会；
- 不是只谈落地而放弃架构方向；
- 不是只谈稳定而拒绝一切改进；
- 不是未经授权的代码改造指令。

# Part VII — 最终交付清单

在诊断/试点模式下，最终响应必须包含：

1. HTML 报告文件路径或可点击链接；
2. 报告是否已成功自动在 Chrome 打开；若失败，诚实说明；
3. 一句话概括当前主要瓶颈与首选突破口；
4. 当前分析的最大未知或风险；
5. 不修改代码的声明。

在执行模式下，最终响应必须额外包含：

1. 实际修改文件清单；
2. 修改与试点假设之间的对应关系；
3. 已运行的验证及结果；
4. 未能运行的验证及原因；
5. 回滚方式；
6. 是否建议扩大试点范围，以及依据。

# Execution Summary

1. 探查项目，建立事实账本；
2. 结合 churn、复杂度、事故/交付拖累与业务影响，找到真正压制发展的主要瓶颈；
3. 区分必须守住的稳定契约与应优先突破的能力阻塞债；
4. 用结果标准而不是技术身份比较候选路线；
5. 选择可控、可观察、可回滚、可复制的第一 `Pilot Cell`；
6. 为其设计 flag/canary/shadow/ACL/Strangler 等适用的过渡机制、逃生舱、稳定红线、负责人与扩散路径；
7. 生成可交互 HTML 优化决策报告；
8. 用户明确授权后，才在试点边界内执行代码变更并验证；
9. 用试点事实决定修正、扩散或停止，而不是为既有理念辩护。
