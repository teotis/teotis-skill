# Operation and evolution

Expand only questions relevant to current risk, frequency, and expected lifetime. These are judgment aids, not files or stages every project needs.

## Safe change: what must be recovered?

For overwrites, migrations, path changes, or external writes, distinguish code, original material, derived data, and external effects. Define protection, cutover scope, and stop conditions for each. Backup existence does not prove recovery: test an isolated restore, reconciliation, or proportionate equivalent. Untested recovery remains missing evidence.

Identify existing edits and usage paths before choosing local repair, boundary change, or replacement. Confirm protection/recovery prerequisites before destructive steps. If rollback is unsafe, describe a forward-repair option and residual risk rather than promising rollback. Verify publication/payment/external-write authorization separately.

## Reliable operation: success, interruption, retry

Compare before/after on one real frequent path: input, entry point, and usable result. Checks/diagrams support this evidence rather than replace it.

Long tasks, batches, or external effects need interruption points, partial success, state authority, and retry semantics. Query/reconcile uncertain results before retrying to avoid duplicate payment, upload, or overwrite. Redo only unfinished parts outside existing success evidence. Unknown outcomes pause the affected side effect while preserving recovery clues.

For automation, identify failure detection, diagnosis, and manual takeover. Successful exit with missing output is still a failure. Short scripts can use clear exits and output checks without a permanent monitoring service.

## Long-term maintenance, failure, and exit

Determine who maintains the mechanism, intervention frequency, and whether entry points, configuration, state, and docs drift independently. A clear maintenance command may be enough for a personal project; an owner system is not mandatory.

When dependencies disappear, can data be read, exported, rebuilt, or handled manually? Preserve irreplaceable originals before regenerating derived assets. Offline degradation is not universally required.

Use a months-later resumption scenario: can the user find entry points, operation instructions, trusted state, and next action? Repair current authorities before adding dashboards or ledgers. Pilot observation/exit criteria should relate to user benefit: repeated work reduction, failure recovery, or maintenance cost versus saved effort. Unmeasured gains remain hypotheses. Permit merge, downgrade, removal, or no-op when value is absent while preserving safety protection.

## Delivery evidence

State verified usage paths, failure cases, and unverified recovery/long-term benefits. Compatibility checks target actual callers, links, and data. Wording-only edits need no invented full regression suite. One trial cannot prove long-term benefit: give observable conditions rather than fabricated usage conclusions.
