# Project-local continuation contract

This is a cold-start affordance, not a form to fill mechanically. Reference native project assets when they already carry the information.

## Minimum sufficient information

Goal/non-goals, recipient's task, trusted current state and sources, decisions, write boundaries and authorization, remaining work, first action, success evidence, and result destination. Unknown tools, branches, and APIs become verify-first steps rather than fictional commands.

When workspace state matters, distinguish pre-existing baseline edits from task-owned edits, identify the result branch and integrated commits, and require current-state revalidation. Stage only task paths. Stop and explain when a conflict cannot preserve both intents; never promise that every merge is safe or that aborting is always forbidden.

## Cross-platform and recovery

Preserve project objects, conventions, relative locations, and validation oracles without binding the recipient to branded tools. Native tools are optional enhancements. Missing tools permit document-based continuation with explicit unknowns, not silent installation or platform changes. Launching sessions, sending messages, paying for calls, and continuous execution each need existing action authorization.

On failure preserve symptoms, attempts, valid inputs/results, state authority, safe continuation point, retry budget, and stop conditions. Resume existing task IDs before creating attempts. Reference an existing scheduler/ledger rather than creating a second runtime truth.

## Placement

Use the target project's docs, notes, task packages, or issue documents; otherwise suggest a dated handoff in docs/handoffs. Durable implementation-adjacent documents may join the project's local mainline after checks; sensitive/scratch material remains ignored. Without an identified target, prepare content but do not write it into an unrelated skill workspace or OS temporary directory.
